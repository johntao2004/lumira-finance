# 基座升级流程

## 版本归属

产品仓库提交记录唯一确定财务源码与基座 gitlink 的组合。submodule 的 `.gitmodules` 仅保存上游地址，不能代替固定提交。财务系统不直接跟随上游 main 自动部署。

通用能力在 Lumira Next 上游开发；财务业务在本仓库开发。升级上游时，财务源码仍在本仓库，不需要维护整份基座的长期分叉。

## 升级操作

先确保产品工作区和 submodule 干净，将下面的 `<已评审的基座提交SHA>` 替换为确定的提交；不要直接运行占位符。

```powershell
git switch -c codex/upgrade-platform
git -C platform/lumira-next fetch origin
git -C platform/lumira-next checkout --detach <已评审的基座提交SHA>
git diff --submodule=log
git add platform/lumira-next
node scripts/prepare-workspace.mjs
```

`git add` 只暂存候选 gitlink，供组装工具验证，不表示已经发布。检查生成工作区中的基座说明，安装依赖并完成相关构建和兼容性验证后，再提交：

```powershell
git commit -m "chore: upgrade Lumira platform"
```

首次使用的基座引用不包含原项目未提交修改。需要这些功能时，先在原项目完成相应修改的验证与提交，供其他机器获取还需发布到上游，然后按本流程更新财务仓库。不要批量代提交原项目未知归属的改动。

## 验证与数据库

- 核查 SDK、插件清单、核心模块精确依赖版本及前后端公开契约的变化；基座版本升级可能要求财务插件适配。
- 在隔离环境执行插件类型检查、宿主和插件构建、相关自动化测试，以及真实浏览器流程验证。
- 财务功能实现后，升级验证应覆盖权限和数据范围、金额精度、事务与幂等，以及该版本实际涉及的业务流程。
- 基座全局初始化 SQL 不是通用升级脚本。涉及已有数据库结构时，先确认该版本明确支持的保数据路径；没有路径时不能直接上线。
- 财务表由财务插件独立管理。插件数据库初始化及演进必须遵守锁定基座契约，不得改写已应用历史。
- 发布前保存数据库备份、插件版本及制品摘要，并验证恢复流程；构建产物、配置、数据和插件版本需要作为配套发布内容管理。

## 回退边界

尚未部署时可以恢复候选 gitlink并重新执行 `git submodule update --init --recursive`。已经部署后，回退源码或镜像不代表数据库也已回退；若执行过结构或数据变更，必须依据该次发布的兼容性与恢复方案处理。

## GitHub 验证与发版

- 为指向 `main` 的 PR（包括 Fork）和 `main` 推送运行 `Finance CI`。它检出已提交指针锁定的公开基座，检查工作区组装、迁移校验和、部署配置及运维测试。检出使用 Actions 自带的只读权限。基座升级 PR 仍需完成上述构建和隔离环境验收。
- `main` 通过 PR 合并，要求 `Verify finance` 通过并禁止强推。
- 完成验收后，在财务仓库对已验收的产品提交创建版本 tag 和 GitHub Release。发行说明记录财务版本、产品提交、基座提交和实际发布制品的 SHA-256。生产部署显式选择对应版本及制品摘要。
